# 🥗 CareView - 개인 맞춤형 식단·운동 추천 서비스

사용자의 **신체 정보, 건강 목표, 알레르기, 보유 식재료**를 기반으로
개인에게 적합한 식단과 운동을 추천하는 맞춤형 헬스케어 서비스입니다.

기존 건강 서비스의 획일적인 추천 방식에서 벗어나, 사용자별 조건을 데이터로 구조화하고 이를 기반으로 **안전한 식단 추천, 운동 처방, 체중 예측** 기능을 제공하는 것을 목표로 개발했습니다.

* 4주 체중 변화 예측

을 제공하는 개인 맞춤형 헬스케어 서비스를 구축했습니다.

## 🗄️ Database Design

사용자와 식단 데이터를 단순한 단일 테이블로 관리하지 않고, **정규화와 N:M 관계를 고려하여 관계형 데이터베이스 구조를 설계**했습니다.

주요 엔티티는 다음과 같습니다.

```text
Users
 │
 ├── Onboarding Config
 │       ├── 신체 정보
 │       ├── 건강 목표
 │       └── 운동 목표
 │
 └── User Allergies
          │
          ▼
      Allergies


Recipes
 │
 ├── Item Ingredient
 │       │
 │       ▼
 │   Ingredients
 │
 └── Cooking Steps
```

### 주요 데이터 관계

* 사용자 ↔ 알레르기 : N:M
* 레시피 ↔ 식재료 : N:M
* 레시피 → 조리 단계 : 1:N
* 사용자 → 건강 설정 : 1:1

이를 통해 식재료 단위의 알레르기 검증과 보유 재료 기반 레시피 검색이 가능하도록 설계했습니다.

## 🍽️ 주요 기능

### 1. 개인 맞춤 식단 추천

사용자의 건강 정보와 알레르기 정보를 기반으로 적합한 레시피를 조회합니다.

특히 단순히 사용자가 입력한 알레르기 이름과 레시피 이름을 비교하는 방식이 아니라, **레시피에 포함된 식재료까지 추적하여 알레르기 유발 식재료가 포함된 레시피를 제외**하도록 구현했습니다.

```text
사용자 알레르기 정보
        ↓
알레르기 유발 식재료 조회
        ↓
해당 식재료가 포함된 레시피 ID 추출
        ↓
NOT IN 필터링
        ↓
안전한 레시피 추천
```

---

### 2. 냉장고 보유 재료 기반 레시피 추천

사용자가 보유하고 있는 식재료를 기반으로 조리 가능한 레시피를 조회합니다.

```text
사용자 보유 식재료
        ↓
Ingredient 매핑
        ↓
Recipe 조회
        ↓
Cooking Steps 매핑
        ↓
추천 레시피 + 조리 과정 제공
```

---

### 3. 개인 맞춤 운동 처방

사용자의 **나이, BMI, 건강 목표**를 기반으로 개인에게 적합한 운동을 추천하도록 구현했습니다.

---

### 4. 4주 체중 예측

사용자의 신체 정보와 목표 데이터를 활용하여 향후 4주간의 체중 변화를 예측하는 기능을 구현했습니다.

## 🔥 Trouble Shooting

### 1. N:M 관계에서 알레르기 식재료 필터링 문제

#### 문제

사용자와 알레르기, 레시피와 식재료가 각각 N:M 관계로 연결되어 있어 여러 개의 알레르기를 가진 사용자가 안전하게 섭취할 수 있는 레시피만 필터링하기 어려웠습니다.

단순 JOIN 방식으로 구현할 경우 중복 데이터가 발생하고 쿼리가 복잡해지는 문제가 있었습니다.

#### 해결

알레르기 유발 식재료가 포함된 레시피 ID를 먼저 서브쿼리로 추출한 뒤, 메인 쿼리에서 `NOT IN` 조건을 적용하는 방식으로 변경했습니다.

```text
[사용자 알레르기]
       ↓
[알레르기 유발 식재료]
       ↓
[해당 식재료가 포함된 Recipe ID]
       ↓
       제외
       ↓
[안전한 Recipe 목록]
```

이를 통해 여러 알레르기를 가진 사용자에 대해서도 알레르기 유발 레시피를 일괄적으로 제외할 수 있도록 구현했습니다.

---

### 2. 레시피 / 식재료 / 조리 단계 데이터 구조 복잡성

#### 문제

하나의 레시피에 여러 식재료가 포함되고, 하나의 식재료가 여러 레시피에서 사용될 수 있었습니다.

또한 레시피별 조리 순서까지 관리해야 했기 때문에 단일 테이블 구조로는 데이터 중복과 관리 문제가 발생했습니다.

#### 해결

데이터를 역할별로 분리하고 중간 테이블을 활용하여 정규화했습니다.

```text
recipes
   ↕
item_ingredient
   ↕
ingredients

recipes
   ↓
cooking_steps
```

이를 통해 식재료 단위의 알레르기 검증과 보유 재료 기반 레시피 추천이 가능하도록 데이터 구조를 개선했습니다.

## 🔐 Authentication

사용자 인증에는 **JWT 기반 Stateless Authentication**을 적용했습니다.

### 인증 흐름

```text
회원가입
   ↓
비밀번호 Hashing
   ↓
사용자 저장
   ↓
로그인
   ↓
Access Token 발급
   ↓
API 요청
   ↓
JWT 검증
   ↓
사용자별 데이터 접근
```

비밀번호는 평문으로 저장하지 않고 해싱하여 저장하며, 인증이 필요한 API에서는 JWT를 검증하여 사용자별 데이터를 처리하도록 구현했습니다.

이 프로젝트를 통해 단순히 API를 구현하는 것뿐만 아니라 **서비스 요구사항을 데이터 구조로 변환하고, 관계형 데이터베이스에서 이를 효율적으로 조회하는 과정**을 경험했습니다.

또한 백엔드 개발 과정에서 API와 데이터베이스의 관계를 직접 설계하며 **데이터가 서비스 로직을 거쳐 사용자에게 전달되는 전체 흐름**을 이해할 수 있었습니다.
